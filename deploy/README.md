# Деплой

Продакшен: VPS с Ubuntu 24.04, сайт https://lamoda-ai-fitting.ru. Деплой автоматический: каждый
merge в `main` → CI собирает и проверяет образы, публикует их в GHCR и разворачивает на сервере
скриптом `deploy/scripts/deploy.sh` (blue-green, без простоя для api и web; инфраструктура — см. «Как идёт деплой»). Как устроены
файлы:

| Что                     | Где                                                                   |
| ----------------------- | --------------------------------------------------------------------- |
| инфраструктура          | `compose/infra.yml` — PostgreSQL, два Redis, Temporal, nginx, certbot |
| копия приложения (цвет) | `compose/app.yml` — api + web, blue или green                         |
| воркер Temporal         | `compose/worker.yml`                                                  |
| бэкапы                  | `compose/backup.yml` — ночная копия базы и бакета («Бэкапы»)          |
| nginx                   | `nginx/` — шаблон конфига, временный сертификат, автоперезагрузка     |
| деплой                  | `scripts/deploy.sh`                                                   |
| подготовка сервера      | `ansible/base.yml`                                                    |
| образы в CI             | `.github/workflows/images.yml`, вызывается из `ci.yml`                |
| CD                      | `.github/workflows/cd.yml`, вызывается из `ci.yml`                    |

## Как идёт деплой

Push в `main` (merge PR) → workflow **CI**: Secret scan и Checks стартуют одновременно, Images —
сразу после успешного Secret scan (секунды; так секрет не попадёт в GHCR и в Sentry). В pull
request все три стартуют одновременно.
Images (`images.yml`) собирает образы, проверяет blue-green деплой на раннере и публикует образы в
GHCR; публикует только job `images-main`, который запускается лишь на push в `main` и один имеет
`packages: write`. Pull request вызывает тот же `images.yml` из `images-pr` с `contents: read` и
ничего не публикует. Когда все три прошли → **CD** (`cd.yml`, окружение `production`):

1. SSH на сервер под `deploy` (ключ сервера сверяется с `DEPLOY_KNOWN_HOSTS`);
2. каталог `deploy/` синхронизируется в `/opt/ai-fitting/deploy` на месте (`rsync --delete`):
   папки не подменяются, иначе работающий nginx продолжал бы видеть старую, удалённую копию;
3. `/opt/ai-fitting/.env` пишется заново из секретов и переменных GitHub — **правки на сервере
   затираются**, менять значения нужно в GitHub;
4. сервер входит в GHCR временным токеном прогона и выходит после деплоя;
5. `deploy.sh <тег>`: базы и Temporal (ничего не делает, если `infra.yml` не менялся) → срок
   хранения истории Temporal → копия базы перед миграциями → миграции → сид демо-каталога → проверка фото из бакета → nginx
   (пересоздаётся, если менялся его сервис в `infra.yml`, и получает новый конфиг) → проверка фото
   через nginx → новая копия рядом со старой → проверка → переключение nginx. Срок хранения истории namespace `default`
   каждый деплой ставит 24 часа (спека 0013 N45): id удалённого пользователя остаётся в истории
   `deleteFiles` не дольше суток, и ни новый образ Temporal, ни новый том этого не меняют. Сид
   добавляет только недостающие строки и не меняет существующие, а в бакет загружает только
   недостающие фото, поэтому при следующем деплое ничего не делает. Проверка фото берёт случайную
   картинку каталога прямо из бакета (из одноразового контейнера нового образа api на сервере, без
   кэша nginx), затем ту же картинку через nginx, и ждёт 200 («Хранилище S3»). Копию базы делает
   одноразовый контейнер образа `ai-fitting-backup` (`deploy/compose/backup.yml`, спека 0012), и
   только если релиз несёт миграцию, которой в базе ещё нет: зашифрованный дамп уходит в бакет
   бэкапов под `pre-deploy/`. Версия без задания бэкапов (старше спеки 0012) копию пропускает;
   версия с ним, чей образ бэкапа не найден или не скачался, останавливает деплой. Упавшая копия,
   миграция, сид или проверка из бакета останавливают деплой до nginx: nginx, его конфиг и `/media/`
   остаются прежними, а сайт продолжает обслуживать старая копия (спека 0011 M38). Откат на копию,
   которая ещё работает, применяет nginx сразу, без копии, миграций, сида и проверок фото. После
   переключения воркер Temporal и задача бэкапов заменяются на месте; если они не стартовали, лог
   пишет предупреждение, а деплой не падает;
6. проверка снаружи: сайт отвечает новой версией;
7. удаляются образы api, web и бэкапов, из которых не создан ни один контейнер: остаются рабочая копия,
   запасная (для отката), воркер и задача бэкапов. Каждый деплой добавляет ~1,7 ГБ, и 2026-10-16 они заполнили
   диск сервера (следующий деплой не смог скачать образ). На сервере то же делается и перед
   скачиванием образов (шаг 5), поэтому заполненный диск не останавливает следующий деплой. Откат на
   более старую версию скачивает её образы из GHCR заново. Лог пишет, сколько образов удалено;
   ошибка очистки пишет предупреждение и деплой не роняет.

Весь путь коммита виден в одном прогоне на вкладке Actions. Деплои идут строго по одному.

Образы попадают в GHCR, не дожидаясь Checks. Если Checks упал, образ этого коммита уже
опубликован, но CD его не развернёт: в GHCR бывают теги, которые никогда не работали на сайте.

Инфраструктура (`compose/infra.yml`) не участвует в blue-green: деплой, в котором изменилось
описание её сервиса, пересоздаёт этот сервис на месте: PostgreSQL, оба Redis и Temporal в начале
`deploy.sh`, до миграций, nginx после сида и проверки фото из бакета. Для
PostgreSQL, `redis`, Temporal и nginx это простой: секунды при смене настроек, дольше при смене
образа; активная копия и воркер Temporal теряют соединения. Пересозданный `redis-cache` не простой,
а пустые кеши: без него сайт работает без кеша (спека 0018 V5). Такие изменения решает владелец и
мержит в тихое время.

Redis два (спека 0018 V4, V10), оба общие для blue и green:

| Сервис        | Что хранит                                                      | Память (`maxmemory` / `mem_limit`) | Когда полон                                                   |
| ------------- | --------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------- |
| `redis`       | счётчики лимитов запросов; до спеки 0018 T5 и счётчики фильтров | 64 MB / 128 MB, без диска          | `noeviction`: запись отказывает, api считает лимиты в памяти  |
| `redis-cache` | кеши (с T5 счётчики фильтров, с T6 страницы; пока пуст)         | 128 MB / 192 MB, без диска         | `allkeys-lru`: вытесняет давно не читанные ключи, запись идёт |

`maxmemory` берётся из `REDIS_MAXMEMORY` и `REDIS_CACHE_MAXMEMORY`; CD их не пишет, поэтому на
сервере действуют значения по умолчанию из `infra.yml`. `redis-cache`, который не стал healthy,
останавливает деплой, как и остальная инфраструктура (V18).

С V20 `redis` ничего не пишет на диск, и том `ai-fitting-infra_redisdata` (локально
`ai-fitting_redisdata`) больше не нужен; compose его не удаляет. Владелец удаляет его руками после
первого успешного деплоя с этим изменением. Откат на версию до него снова смонтирует том, но ключи
в старом снимке давно истекли.

## Лимиты nginx

Грубая страховка до Node, выше квот самого api (спека 0006 F7, F8, F32–F37, спека 0014 O19, O39; значения в
`nginx/templates/default.conf.template`):

| Что                                                             | Лимит на адрес клиента                                   | Ответ сверх него                                     |
| --------------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- |
| запросы к `/api/`                                               | 20 в секунду, всплеск до 40 сверх темпа                  | 429 `TOO_MANY_REQUESTS`                              |
| запросы к `/socket.io/`                                         | 10 в секунду, всплеск до 20 сверх темпа                  | 429 `TOO_MANY_REQUESTS`                              |
| запросы к `/api/health/live`                                    | 50 в секунду, всплеск до 100 сверх темпа                 | 429 `TOO_MANY_REQUESTS`                              |
| страницы web (`/`, кроме GET статики `/_next/static/`)          | 33 в секунду, всплеск до 33 сверх темпа                  | 429 `TOO_MANY_REQUESTS`                              |
| фото `/media/`                                                  | 30 в секунду, всплеск до 60 сверх темпа                  | 429 `TOO_MANY_REQUESTS`                              |
| соединения `/socket.io/` (сокеты и long-polling)                | 10 одновременно                                          | 429 `TOO_MANY_REQUESTS`                              |
| запросы в работе на всём сайте (и сокеты)                       | 50 одновременно                                          | 429 `TOO_MANY_REQUESTS`                              |
| медленный клиент: заголовки, пауза в теле или при чтении ответа | 10 с; простой keep-alive 15 с (редиректы без keep-alive) | соединение закрывается без ответа (408 в логе nginx) |
| тело запроса                                                    | 1 МБ (весь сайт, не на адрес)                            | 413 `PAYLOAD_TOO_LARGE`                              |
| ответ api                                                       | 60 с; api сам отвечает 503 не позже ~31 с                | 503 `SERVICE_UNAVAILABLE`                            |

Ответы nginx — в формате ошибок api (`{ error: { code, message, details } }`), 502 и 504 на
`/api/` тоже становятся 503. Лимиты страниц и фото — трижды пик одного визита в каталог, замеренного
на проде скриптом `scripts/measure-page-requests.mjs` (спека 0014 O24, O109; у фото всплеск — одна
порция в 60 карточек, O110): после заметных изменений страниц визит перемеряют. Статика Next
(GET и HEAD к `/_next/static/`) под лимит запросов в секунду не попадает, только под лимит запросов
в работе; запрос со «сложным» путём (`%2F`, `%2e`, `..`, `\`), другим методом или заголовком
`Range`/`If-Match`/`If-Unmodified-Since` считается страницей: по нему Next может отрендерить
страницу ошибки (O111);
`/healthz` (проверка здоровья контейнера web) снаружи отвечает 404. `/api/socket.io` закрыт (404),
иначе socket.io за `/api/` обходил бы лимит соединений. Соединение, которое ещё не дослало заголовки, не видит ни один лимит
nginx: его ограничивает только таймаут в 10 с.
Посетители за одним NAT делят лимит. nginx не ограничивает размер WebSocket-кадров: это делает api
(`SOCKET_MAX_MESSAGE_BYTES`). `worker_connections` остаётся 1024 на воркер из образа (сокет
занимает два соединения); когда их не хватает, в логе nginx «worker_connections are not enough».
Поднять — свой `nginx.conf` и больший `nofile`. Проверяет `scripts/ci-deploy-check.sh`.
Content Security Policy страниц web и то, как nginx её пропускает, — в «Заголовках безопасности»
(раздел «Сертификат HTTPS»).

## Откат

Предыдущая версия остаётся запущенной (запасной цвет), откат на неё занимает секунды:

1. Actions → **CD** → **Run workflow** → `image_tag` = 7 символов хеша нужного коммита из `main`;
2. либо из терминала: `gh workflow run cd.yml -f image_tag=<хеш>`.

Откатывать можно только на хеш, который уже был на сайте: прогон CI этого коммита дошёл до
зелёного CD. Опубликованный образ коммита, у которого упал Checks, на сайт никогда не попадал.
CD, запущенный вручную, сам проверяет это (шаг «Check that the tag was live»: у коммита должен
быть успешный check run `CD / Deploy to production`) и отказывает до любого действия на сервере.
Если CD коммита упал сам по себе (например, сбой сети), его перезапускают в прогоне CI
(**Re-run failed jobs**), а не вручную.

Откат на ещё запущенную копию применяет nginx (пересоздаёт, если менялся его сервис) и
переключает его: миграций, сида и проверки фото в нём нет. Если `.env` или `compose/app.yml`
изменились с её запуска (сменили `PROXY_SECRET`, добавили или убрали переменную), копия сначала
пересоздаётся (секунд 20, трафик пока идёт на текущую копию); если она не поднимется, её
останавливают, и сайт остаётся на текущей. Откат на более старую версию — тот же запуск, только
это полный деплой (~1 мин). Откат не возвращает миграции базы назад: поэтому миграции всегда
совместимы с предыдущим релизом (`specs/principles.md`). В образе, собранном до появления сида,
шага нет: деплой пишет «seed skipped» и идёт дальше.

Откат на версию до PR 3 спеки 0014 (до страницы каталога) не поднимается: проверка здоровья web из
`compose/app.yml` (она берётся из `main`) спрашивает `/healthz`, которого в старом образе нет, новая
копия web не становится здоровой, деплой останавливается, и сайт остаётся на работающей копии
(спека 0014 O70). Вернуться к такой версии можно только revert'ом в `main` через CI и CD.

Какой цвет и тег сейчас обслуживают сайт, какие проекты compose запущены (`ai-fitting-infra`,
`-blue`, `-green`, `-worker`), последние 50 строк лога api копии blue (для green —

```bash
ssh ai-fitting 'cat /opt/ai-fitting/.deploy-state'

```

## Подготовка Mac (один раз)

`deploy.sh` нужен bash 4+:

```bash
brew install ansible bash
```

В `~/.ssh/config` — алиас сервера (адрес и ключ только здесь, не в репозитории):

```
Host ai-fitting
  HostName <IP сервера>
  User root
  IdentityFile ~/.ssh/<ключ владельца>
  IdentitiesOnly yes
```

Проверка: `ssh ai-fitting hostname`.

## Подготовка сервера (один раз, повторный запуск безопасен)

1. **Ключ для CI.** Отдельный ключ, которым GitHub Actions заходит на сервер как пользователь
   `deploy`. Создаётся на Mac, в репозиторий не попадает:

   ```bash
   ssh-keygen -t ed25519 -N "" -C "ai-fitting CI deploy" -f ~/.ssh/ai-fitting-ci
   ```

   Открытая часть (`.pub`) уходит на сервер через плейбук, закрытая — только в секрет GitHub
   `DEPLOY_SSH_KEY` (раздел «Настройки GitHub»).

2. **Плейбук.** Имя сервера `ai-fitting`, Docker и Compose, ротация логов Docker, firewall (входящие
   только 22, 80, 443/tcp), swap 2 ГБ, пользователь `deploy` (группа `docker`, без пароля и без sudo,
   вход только по ключу CI), каталог `/opt/ai-fitting`. Запуск с `--check --diff` показывает, что
   изменится, ничего не меняя; затем запуск без флагов:

   ```bash
   cd deploy/ansible
   ansible-playbook base.yml --check --diff
   ansible-playbook base.yml
   ```

   Ожидаемо: `failed=0`; при повторном запуске `changed=0`.

3. **Проверка входа CI:**

   ```bash
   ssh -i ~/.ssh/ai-fitting-ci -o IdentitiesOnly=yes deploy@<IP сервера> 'hostname; docker ps'
   ```

Пользователь `deploy` в группе `docker` фактически может управлять контейнерами сервера. Выигрыш
отдельного пользователя — отдельный ключ: его можно отозвать (`exclusive` в плейбуке заменяет
ключи), не трогая доступ владельца, и в логах сервера видно, что делал CI.

## Хранилище S3

Один закрытый бакет приложения в Timeweb Cloud (спека 0011). Первый сегмент ключа — его класс:
`media/` — фото каталога, без срока; `keep/users/<id>/…` — фото пользователей и результаты
генераций, без срока; `tmp/` — незаконченные загрузки, удаляются через сутки. Ничего не публично:
`media/` читает без ключа только адрес сервера, остальное — только api со своим ключом или по
подписанной ссылке (15 минут). Бэкапы базы и этого бакета лежат в отдельном бакете; там же, в
«Бэкапах», — как их восстановить.

nginx отдаёт `/media/<ключ>` из `media/<ключ>` бакета на том же домене (`MEDIA_BASE_URL`
остаётся `https://lamoda-ai-fitting.ru/media/`). В хранилище уходят только ключ и `Host`: ни
заголовков посетителя (секрет прокси, адрес, cookies), ни query string. Заголовки хранилища из
списка в `nginx/templates/default.conf.template` скрыты (список, не маска: новые метаданные объекта
добавляются туда), `Cache-Control` объекта (сутки) остаётся. Кэш nginx: фото — сутки, отказ —
минуту; если хранилище недоступно (нет соединения, таймаут, ответ 5xx), отдаётся устаревшая копия,
когда она есть в кэше (фото, которое спрашивали за последние 7 дней). Нет ключа, `/media/` сам по себе или ключ на
`/` — 404 `NOT_FOUND`; метод кроме `GET`/`HEAD` — 404 `ROUTE_NOT_FOUND`; хранилище упало или
недоступно, а копии в кэше нет — 503 `SERVICE_UNAVAILABLE`. `S3_ENDPOINT` и `S3_BUCKET` есть и у nginx в `infra.yml`:
их смена пересоздаёт nginx (несколько секунд простоя).

Настройка, один раз (сделана 2026-10-16):

1. В панели Timeweb: бакет — приватный, класс Standard, 10 ГБ; дополнительный пользователь с
   правом «Чтение и запись» на этот бакет: его ключ — секреты `S3_ACCESS_KEY_ID`,
   `S3_SECRET_ACCESS_KEY` («Environment `production`» ниже), не ключ главного пользователя.
2. Политика бакета: чтение `media/*` без ключа только с адреса сервера. В панели её задать
   нельзя: она ставится через `aws-cli` в одноразовом контейнере на сервере, с ключом главного
   пользователя, который никуда не сохраняется. На сервере (`ssh ai-fitting`) файл
   `policy.json`:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Principal": "*",
         "Action": "s3:GetObject",
         "Resource": "arn:aws:s3:::<бакет>/media/*",
         "Condition": { "IpAddress": { "aws:SourceIp": "<IP сервера>/32" } }
       }
     ]
   }
   ```

   Затем ключ главного пользователя. Эти строки вставлять по одной: `read` без них заберёт
   следующую строку блока, а ключ, набранный в приглашение shell, попадёт в историю. Ввод не
   отображается; история этой сессии не пишется в файл:

   ```bash
   unset HISTFILE
   read -rsp 'Access key ID: ' AWS_ACCESS_KEY_ID; echo
   read -rsp 'Secret key: ' AWS_SECRET_ACCESS_KEY; echo
   export AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
   ```

   Политика (образ закреплён по дайджесту: он получает главный ключ) и уборка:

   ```bash
   docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY \
     --mount type=bind,src="$PWD/policy.json",dst=/policy.json,readonly \
     amazon/aws-cli:2.17.0@sha256:643507c10ada7964ca6157b3d799f030b90577643da9955d319a77399ed80d73 \
     s3api put-bucket-policy --endpoint-url https://s3.twcstorage.ru --region ru-1 \
     --bucket <бакет> --policy file:///policy.json
   unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
   rm policy.json
   ```

   Если ключ мог попасть в историю или на экран, перевыпустить его в панели.

   Проверка: тестовые объекты `media/check.txt` и `keep/check.txt` в панели, затем
   `curl -I https://s3.twcstorage.ru/<бакет>/media/check.txt` с сервера (`ssh ai-fitting`) — 200,
   с Mac — отказ; `…/keep/check.txt` с сервера — отказ. Если с сервера тоже отказ, Timeweb видит
   его запросы с другого адреса (внутренняя сеть): к выбору доступа к `media/` возвращаемся
   (спека 0011 M15). Тестовые объекты потом удалить.

3. Правило жизненного цикла: префикс `tmp/`, удалять объекты через 1 день и прерывать незаконченные
   загрузки через 1 день.
4. Секреты и переменные `production` — в «Environment `production`» ниже.

Проверить запись с Mac нельзя: production-ключей на нём нет (`CONTRIBUTING.md`, п. 4). Запись
проверяет первый деплой: сид загружает фото каталога, затем `deploy.sh` проверяет одно из них.

**Убрать фото каталога.** Ключ в `media/` никогда не перезаписывается: новое фото получает новый
ключ. Поэтому nginx отдаёт копию из кэша и тогда, когда хранилище отвечает 5xx (спека 0011 M36),
до 7 дней после последнего запроса. Если фото нужно убрать (например, по жалобе), после удаления
объекта в панели очистить кэш nginx (подтверждает владелец, команда меняет сервер):

```bash
ssh ai-fitting 'docker exec ai-fitting-infra-nginx-1 sh -c "rm -rf /var/cache/nginx/media/*"'
```

**Новый адрес сервера.** Политика пускает в `media/` только старый адрес: сначала добавить новый
адрес в политику (шаг 2, `"aws:SourceIp"` принимает список) (а старый убрать после переезда), потом переезжать. Иначе `/media/` отвечает 404,
а деплой останавливается на проверке фото из бакета («the server cannot read the media from the
bucket»), не меняя nginx. Отказ nginx держит в кэше минуту: после исправления политики `/media/`
оживает не сразу.

## Бэкапы

Каждую ночь в 04:00 по Москве задача бэкапов (проект `ai-fitting-backup`, `compose/backup.yml`,
спека 0012) копирует базу и бакет приложения (кроме `tmp/`) в отдельный бакет бэкапов. Копии
зашифрованы открытым ключом age владельца: на сервере и в GitHub лежит только он, закрытый ключ —
только в менеджере паролей владельца. Копии живут 7 дней. Кроме того, деплой с новой миграцией
перед ней кладёт копию базы под `pre-deploy/` («Как идёт деплой»). Задача — свой контейнер, который
каждый деплой заменяет на месте после воркера Temporal. Она читает бакет приложения ключом, который
может только читать, а пишет ключом, который может только загружать: кто прочитает `.env` сервера,
копий не прочтёт и не удалит. Каждый запуск отмечается в мониторе Sentry `nightly-backup` (проект
api): упавший или не начавшийся запуск — письмо владельцу.

Настройка, один раз, до первого деплоя с задачей: без её переменных CD останавливается (сделана
2026-10-19, кроме шага 6).

1. В панели Timeweb: бакет — приватный, класс Standard (холодный был распродан, спека 0012 P20),
   минимальный объём; версионирование включено; правила жизненного цикла: удалять объекты через 7
   дней, неактуальные версии — через 7 дней, прерывать незаконченные загрузки через 1 день. До
   аренды проверить в панели, что класс даёт версионирование и все три правила; если нет —
   остановиться и решать заново (спека 0012 P2, P12). Версии — вторая линия: если имя копии всё
   же станет известно, ключ записи может её перезаписать, но прежняя остаётся версией, которую он
   не удалит (живёт до 14 дней). Пользователю приложения (ключ `S3_ACCESS_KEY_ID`, «Хранилище S3») доступа к этому
   бакету не давать: его «Чтение и запись» удаляет, и утёкший `.env` удалил бы все копии.
   Оба пользователя создаются в панели Timeweb, «Хранилище» → «Пользователи»
   (https://timeweb.cloud/my/storage/users), и получают свою роль в настройках пользователя. Готовые
   наборы прав не подходят: в «Чтение и запись» есть удаление, а «Чтение» по документации Timeweb не
   даёт списка объектов. `put-bucket-policy` («Хранилище S3») для этого не применять: он заменил бы
   политику `media/` бакета приложения.

2. Пользователь `backup-writer`, роль: только `s3:PutObject` и `s3:AbortMultipartUpload` на
   `arn:aws:s3:::<бакет бэкапов>/*`. Ни чтения, ни списка, ни удаления. В имени каждой копии
   случайная часть, которой нет ни в логах, ни в CI, а списка у этого ключа нет: угадать имя копии,
   чтобы её перезаписать, им нельзя (спека 0012 P27).
3. Пользователь `backup-reader`, роль: `s3:ListBucket` на `arn:aws:s3:::<бакет приложения>` и
   `s3:GetObject` на `arn:aws:s3:::<бакет приложения>/media/*` и `…/keep/*` (`tmp/` задача не
   копирует).
4. Ключ age на Mac (`brew install age`), в обычном терминале, не в сессии агента: закрытый ключ —
   в менеджер паролей, открытый — в GitHub. Потерянный закрытый ключ — потерянные копии:
   расшифровать их больше нечем, поэтому открытый ключ уходит в GitHub только после проверки
   записи в менеджере. Все блоки — в одном терминале, по одному. На время шага выключить Handoff
   (Системные настройки → Основные → AirDrop и Handoff) и историю буфера обмена, если её ведёт
   какое-то приложение: иначе ключ останется и там. Ключ во временную папку вне репозитория,
   закрытая строка `AGE-SECRET-KEY-1…` — в буфер обмена:

   ```bash
   d="$(mktemp -d)"
   age-keygen -o "$d/key" 2>/dev/null
   grep '^AGE-SECRET-KEY-' "$d/key" | pbcopy
   ```

   Вставить её в новую запись менеджера паролей и сохранить. Затем скопировать ключ обратно из
   сохранённой записи и сверить его с файлом (буфер очищается в конце):

   ```bash
   [ "$(pbpaste | age-keygen -y)" = "$(age-keygen -y "$d/key")" ] && echo "запись верна"
   pbcopy < /dev/null
   ```

   Если «запись верна» не напечаталось, исправить запись в менеджере и повторить этот блок (или,
   отказавшись от ключа, `rm -r "$d"`). Только если напечаталось — открытый ключ в GitHub и уборка:

   ```bash
   age-keygen -y "$d/key" | gh variable set BACKUP_AGE_RECIPIENT --env production
   rm -r "$d"
   unset d
   ```

5. Ключи обоих пользователей и имя бакета — в GitHub («Environment `production`» ниже). Это
   ключи `backup-reader` и `backup-writer`, не главного пользователя и не приложения: с ними
   утёкший `.env` удалил бы копии. CD отказывает, если любые два из трёх ключей совпадают.
6. В Sentry, после первой ночи (монитор появляется с первым запуском): правило оповещения на
   issues монитора `nightly-backup` с письмом владельцу.

### Восстановление

Восстанавливает владелец на Mac (`brew install age`, Docker запущен), в обычном терминале, не в
сессии агента: нужны закрытый ключ age из менеджера паролей и ключ главного пользователя Timeweb.
Ни один ключ задачи для этого не годится: `backup-writer` не читает и не видит список,
`backup-reader` не видит бакет бэкапов. Имя копии кончается случайной частью, которой нет ни в
одном логе (спека 0012 P27), поэтому копию находят только по списку. Расшифрованная база живёт
только в одноразовом контейнере, расшифрованные файлы бакета — в папке `~/restore.noindex`, которая в
конце удаляется. Процедура восстанавливает копию в пустую базу и пустой бакет; возврат файлов в
бакет приложения описан в шаге 7, возврат базы на продакшен — в «Возврате базы на продакшен» ниже. Шаги «при проверке» (пункт
бэклога «Production checks of the backups», AC11 и AC12 спеки 0012) сверяют копию с продакшеном.

1. **Оболочка и папка.** Все блоки — в одном терминале, по одному, в bash без настроек: в zsh,
   оболочке терминала Mac по умолчанию, `read -rsp` не читает ключ, и вставленный следом ключ
   уходит в командную строку и историю. Сначала одна эта строка, отдельно: вставленная вместе с
   остальными, она запустит bash, а остальное zsh выполнит только после выхода из него:

   ```bash
   bash --noprofile --norc
   ```

   Папка — вне Time Machine и Spotlight (`.noindex`): в ней окажутся расшифрованные файлы
   пользователей. В ней же запрос, который считает строки каждой таблицы, и скрипт расшифровки
   (шаг 5; он записывается заранее, потому что, пока в буфере обмена ключ age, вставлять нечем;
   буфер он очищает и тогда, когда прерван):

   ```bash
   unset HISTFILE
   mkdir -p ~/restore.noindex/data/storage && tmutil addexclusion ~/restore.noindex && cd ~/restore.noindex
   cat > decrypt.sh <<'SH'
   set -eo pipefail
   trap 'pbcopy < /dev/null' EXIT
   cd ~/restore.noindex/data
   age -d -i <(pbpaste) database.dump.age | docker exec -i restore-db pg_restore --no-owner --exit-on-error -U postgres -d postgres
   if [ -f storage.tar.age ]; then age -d -i <(pbpaste) storage.tar.age | tar -x -C storage; fi
   echo "расшифровано"
   SH
   cat > row-counts.sql <<'SQL'
   SELECT format('%I.%I', table_schema, table_name),
          (xpath('/row/n/text()', query_to_xml(
            format('SELECT count(*) AS n FROM %I.%I', table_schema, table_name), false, true, '')))[1]::text
   FROM information_schema.tables
   WHERE table_type = 'BASE TABLE' AND table_schema NOT IN ('pg_catalog', 'information_schema')
   ORDER BY 1;
   SQL
   ```

2. **При проверке — снимок продакшена.** Строки продакшена и сразу за ними копия вне расписания
   (`--once` в работающем контейнере задачи; в мониторе Sentry она не отмечается). Не с 03:50 по Москве до
   конца ночной копии (`ssh ai-fitting 'docker logs --tail 5 ai-fitting-backup-backup-1'`): две
   копии сразу делят один лимит памяти контейнера.

   ```bash
   ssh ai-fitting "docker exec -i ai-fitting-infra-postgres-1 sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -AtX'" < row-counts.sql > production.txt
   ssh ai-fitting 'docker exec ai-fitting-backup-backup-1 node dist/backup/main.js --once'
   ```

   Вход через Google между этими двумя командами добавит строку в `sessions` или `verifications`:
   разница только в этих таблицах — не ошибка восстановления.

3. **Ключ главного пользователя.** Строки вставлять по одной (почему — «Хранилище S3», шаг 2):

   ```bash
   read -rsp 'Access key ID: ' AWS_ACCESS_KEY_ID; echo
   read -rsp 'Secret key: ' AWS_SECRET_ACCESS_KEY; echo
   export AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
   ```

   `aws-cli` в одноразовом контейнере (образ закреплён по дайджесту: он получает главный ключ),
   ему видна только папка `data` (как `/aws`): скачанное из бакета бэкапов не может заменить
   скрипты шага 1 рядом с ней:

   ```bash
   s3() { docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY --mount type=bind,src="$HOME/restore.noindex/data",dst=/aws amazon/aws-cli:2.17.0@sha256:643507c10ada7964ca6157b3d799f030b90577643da9955d319a77399ed80d73 --endpoint-url https://s3.twcstorage.ru --region ru-1 "$@"; }
   ```

   При проверке — сразу список ключей и размеров `media/` и `keep/` бакета приложения (фото,
   загруженное после копии, покажется лишней строкой продакшена, удалённое — лишней строкой
   восстановленного):

   ```bash
   for p in media/ keep/; do s3 s3api list-objects-v2 --bucket <бакет приложения> --prefix "$p" --query 'Contents[].[Key,Size]' --output text; done | grep -vx None | sort > production-bucket.txt
   ```

4. **Найти копию.** Ночные копии лежат в `daily/`, копии перед миграциями — в `pre-deploy/`
   (там только база). Имя папки начинается временем UTC, поэтому самая свежая — последняя; за одну
   ночь их может быть две (спека 0012 P15). Ключ записи с сервера может добавить и свою папку с
   любым именем: папка не ко времени ночной копии (около 01:00 UTC) или деплоя подозрительна, а
   скачиваются только два известных файла, по имени (для `pre-deploy/` — только первый):

   ```bash
   s3 s3 ls s3://<бакет бэкапов>/daily/
   s3 s3 cp --only-show-errors s3://<бакет бэкапов>/daily/<папка>/database.dump.age /aws/
   s3 s3 cp --only-show-errors s3://<бакет бэкапов>/daily/<папка>/storage.tar.age /aws/
   ```

   Без терминала копию можно скачать и в панели Timeweb, в `~/restore.noindex/data`. Бакет для восстановления (новый, пустой,
   приватный; при проверке — удалить после неё) создать в панели сейчас: следующий шаг занимает
   буфер обмена.

5. **Расшифровка.** Пустой PostgreSQL той же версии, что на сервере, в одноразовом контейнере без
   сети (с `--rm` данные уходят вместе с ним):

   ```bash
   docker run -d --rm --network none --name restore-db -e POSTGRES_PASSWORD=restore postgres:18.6-trixie
   until docker exec restore-db pg_isready -q -h 127.0.0.1 -U postgres; do sleep 1; done
   ```

   Закрытый ключ age — скопировать из записи менеджера паролей в буфер обмена (Handoff и историю
   буфера выключить, как в шаге 4 настройки), затем набрать вручную (не вставлять: в буфере ключ)
   `bash decrypt.sh`. Скрипт из шага 1 ведёт базу прямо в контейнер, бакет — в пустую папку
   `data/storage`, никогда с `-P`: tar пропускает ключ с `..` и убирает ведущий `/`, так что ничего
   не пишется вне папки (спека 0012 P19). Неверный ключ age отвечает:
   `no identity matched any of the recipients`.

6. **При проверке — база:** те же строки, что на продакшене.

   ```bash
   docker exec -i restore-db psql -U postgres -d postgres -AtX < row-counts.sql > restored.txt
   diff production.txt restored.txt && echo "строки совпадают"
   ```

7. **Бакет.** Дерево — в бакет из шага 4. `.DS_Store`, которые Finder оставляет в открытых папках,
   не загружаются; символьные ссылки тоже (в бакете их не бывает, а ссылка из подложенной копии
   выгрузила бы файл, на который указывает):

   ```bash
   s3 s3 sync --only-show-errors --no-follow-symlinks --exclude '*.DS_Store' /aws/storage/ s3://<новый бакет>/
   ```

   При проверке — те же ключи с теми же размерами. Ключи с `..` или ведущим `/`, пустые «папки» с
   `/` на конце и ключи, отличающиеся только регистром (файловая система Mac его не различает), не
   возвращаются как были и покажутся разницей:

   ```bash
   for p in media/ keep/; do s3 s3api list-objects-v2 --bucket <новый бакет> --prefix "$p" --query 'Contents[].[Key,Size]' --output text; done | grep -vx None | sort > restored-bucket.txt
   diff production-bucket.txt restored-bucket.txt && echo "ключи и размеры совпадают"
   ```

   Только при настоящей потере файлов, не при проверке — возврат в бакет приложения. В копии нет
   метаданных объектов: `sync` ставит `Content-Type` по расширению и не ставит `Cache-Control`.
   Поэтому возврат — двумя командами, без `--delete`: `media/`
   с `Cache-Control` сида, `keep/` без него (нет `keep/` в копии — вторая команда скажет, что
   папки нет). Вместе с файлами возвращаются и пользователи, удалённые после копии (спека 0012
   P14).

   ```bash
   s3 s3 sync --only-show-errors --no-follow-symlinks --exclude '*.DS_Store' --cache-control 'public, max-age=86400' /aws/storage/media/ s3://<бакет приложения>/media/
   s3 s3 sync --only-show-errors --no-follow-symlinks --exclude '*.DS_Store' /aws/storage/keep/ s3://<бакет приложения>/keep/
   ```

8. **Уборка** — и после прерванного шага (последняя строка закрывает bash шага 1). При проверке
   затем удалить в панели бакет из шага 4.

   ```bash
   pbcopy < /dev/null
   docker rm -fv restore-db
   unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
   unset -f s3
   cd ~ && rm -r ~/restore.noindex
   exit
   ```

   Если какой-то ключ мог попасть в историю или на экран: главный — перевыпустить в панели, age —
   сменить (ниже).

### Возврат базы на продакшен

Когда база продакшена потеряна или испорчена (спека 0012 P31). Всё это время сайт не работает.
Если причина — неудачная миграция, сначала откатить код на версию до неё (CD вручную, «Откат»), а
копию взять из `pre-deploy/` того деплоя. Сначала шаги 1 и 3 «Восстановления» (оболочка, главный
ключ) и из шага 4 — только поиск и скачивание копии в `data/`; дальше — в том же bash, в конце — его
уборка (шаг 8).

Копия возвращает и то, что удалили после неё (спека 0012 P14): пользователей, примерки и
генерации. Удалённое за последние сутки видно по истории `deleteFiles` в Temporal (спека 0013 N45)
и удаляется снова; в истории нет удалённых примерок без генераций (им нечего удалять в бакете) и
удалений, чей запуск `deleteFiles` не удался (они — в Sentry и логе api, «Could not start the
deletion of files», с видом и id: их добавить в списки шага 4 вручную). Пользователей, примерки и
генерации, которых нет в старой базе (если она читается), процедура показывает отдельными списками:
это удалённые позже или потерянные порчей, их проверяют глазами. Без старой базы удалённое раньше
суток возвращается. Пользователи,
созданные после копии, пропадают: они войдут через Google заново, как новые, а их папки удаляет шаг 7. Файлы, загруженные после копии пользователями, которые в ней есть, остаются в их папках без
строк.

1. **Скрипты** — до ключа age в буфере, как `decrypt.sh`: возврат копии с Mac по ssh одной
   транзакцией (закрытый ключ на сервер не попадает), `psql` базы продакшена, читающий SQL из
   stdin, и две функции: `uuids` пропускает только строки-uuid, `del` удаляет строки таблицы по
   файлу с id. Сортировка — `LC_ALL=C`, как у PostgreSQL для uuid, иначе `comm` сравнит неверно:

   ```bash
   cd ~/restore.noindex
   export LC_ALL=C
   cat > to-production.sh <<'SH'
   set -eo pipefail
   trap 'pbcopy < /dev/null' EXIT
   cd ~/restore.noindex/data
   age -d -i <(pbpaste) database.dump.age | ssh ai-fitting "docker exec -i ai-fitting-infra-postgres-1 sh -c 'pg_restore --no-owner --exit-on-error --single-transaction -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\"'"
   echo "копия на продакшене"
   SH
   cat > psql.sh <<'SH'
   ssh ai-fitting "docker exec -i ai-fitting-infra-postgres-1 sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -AtX -v ON_ERROR_STOP=1'"
   SH
   uuids() { grep -xE '[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}' | sort -u; }
   del() { [ -s "$2" ] && sed "s/.*/'&'/" "$2" | paste -sd, - | sed "s/.*/DELETE FROM $1 WHERE id IN (&);/" | bash psql.sh; }
   ```

2. **Деплои выключить**, чтобы слияние в `main` не задеплоило посреди работы. CD вызывается из CI,
   поэтому выключаются оба. В списке запусков не должно быть `in_progress`, `queued`, `waiting` или
   `pending`: такой отменить (`gh run cancel <id> -R EvaFridman/lamoda-ai-fitting`) или дождаться.
   Затем на сервере берётся замок, которым `deploy.sh` не даёт идти двум деплоям сразу; если он не
   взялся, деплой идёт сейчас — дождаться и повторить:

   ```bash
   gh workflow disable ci.yml -R EvaFridman/lamoda-ai-fitting
   gh workflow disable cd.yml -R EvaFridman/lamoda-ai-fitting
   gh run list --branch main --limit 5 -R EvaFridman/lamoda-ai-fitting
   ssh -n ai-fitting 'mkdir /opt/ai-fitting/.deploy-lock' && echo "замок взят"
   ```

3. **Остановка api и воркера.** Сначала запоминается, что работало (после неудачного деплоя один
   цвет уже остановлен, и запускать его не надо), затем api и воркер останавливаются: с этой минуты
   никто ничего не удаляет:

   ```bash
   ssh -n ai-fitting "docker ps --format '{{.Names}}'" | grep -xE 'ai-fitting-(blue|green)-api-1|ai-fitting-worker-temporal-worker-1|ai-fitting-backup-backup-1' > running.txt
   cat running.txt
   ssh -n ai-fitting "docker stop $(grep -v backup running.txt | paste -sd' ' -)"
   ```

4. **Что сохранить из старого.** Удалённое за сутки — из истории Temporal, по видам:

   ```bash
   ssh -n ai-fitting "docker exec ai-fitting-infra-temporal-1 temporal workflow list -q \"WorkflowType='deleteFiles'\" --limit 10000" > workflows.txt
   for kind in user session generation; do grep -o "delete-files-$kind-[0-9a-f-]*" workflows.txt | sed "s/^delete-files-$kind-//" | uuids > "deleted-$kind.txt"; done
   wc -l deleted-*.txt
   ```

   Если старая база ещё читается — её копия (не с 03:50 по Москве до конца ночной: шаг 2
   «Восстановления») и id её пользователей, примерок и генераций. Файл `before-<таблица>.txt`
   появляется, только если запрос прошёл (пустая таблица даёт пустой файл):

   ```bash
   ssh -n ai-fitting 'docker exec ai-fitting-backup-backup-1 node dist/backup/main.js --once'
   for t in users fitting_sessions ai_generations; do echo "SELECT id FROM $t;" | bash psql.sh > "before-$t.raw" && uuids < "before-$t.raw" > "before-$t.txt"; done
   ls before-*.txt
   ```

   Нет задачи бэкапов в `running.txt` — копию вместо первой строки делает одноразовый контейнер,
   как в деплое:

   ```bash
   ssh -n ai-fitting 'cd /opt/ai-fitting && . ./.deploy-state && IMAGE_TAG="$TAG" docker compose -f deploy/compose/backup.yml --env-file .env run --rm -T backup node dist/backup/main.js --once'
   ```

   Затем задача бэкапов тоже останавливается:

   ```bash
   ssh -n ai-fitting 'docker stop ai-fitting-backup-backup-1'
   ```

5. **Копия.** База пересоздаётся пустой:

   ```bash
   ssh -n ai-fitting "docker exec ai-fitting-infra-postgres-1 sh -c 'dropdb -U \"\$POSTGRES_USER\" --force \"\$POSTGRES_DB\" && createdb -U \"\$POSTGRES_USER\" \"\$POSTGRES_DB\"'"
   ```

   Закрытый ключ age — в буфер обмена (как в шаге 5 «Восстановления»), затем набрать вручную
   `bash to-production.sh`. Не напечаталось «копия на продакшене» — транзакция откатилась, база
   пуста: повторить оба действия. Потом миграции работающей версии, из её образа, как в деплое
   (копия свежая — им нечего применять):

   ```bash
   ssh -n ai-fitting 'cd /opt/ai-fitting && . ./.deploy-state && COLOR="$COLOR" IMAGE_TAG="$TAG" docker compose -p "ai-fitting-$COLOR" -f deploy/compose/app.yml --env-file .env run --rm --no-deps -T api npx --no-install prisma migrate deploy'
   ```

6. **Сессии и удалённое после копии.** Все сессии удаляются: иначе вернулись бы и те, из которых
   вышли после копии; кто входил, войдёт заново (подписанная копия сессии в cookie живёт ещё до
   5 минут, спека 0013 N18). Затем удалённое за сутки — пользователи каскадом, с сессиями,
   аккаунтами, примерками и генерациями:

   ```bash
   printf 'DELETE FROM sessions;\nDELETE FROM verifications;\n' | bash psql.sh
   del users deleted-user.txt
   del fitting_sessions deleted-session.txt
   del ai_generations deleted-generation.txt
   ```

   Если есть файлы `before-*.txt` — строки, которых не было в старой базе, по таблицам:

   ```bash
   for t in users fitting_sessions ai_generations; do [ -f "before-$t.txt" ] && echo "SELECT id FROM $t;" | bash psql.sh | uuids | comm -23 - "before-$t.txt" > "maybe-$t.txt"; done
   wc -l maybe-*.txt
   ```

   Их удалять, только если старая база была цела (не после неудачной миграции или порчи, иначе в
   списках и потерянные ею живые строки) и список похож на удалённое за время после копии; каждую
   таблицу — своей командой, после проверки её списка:

   ```bash
   del users maybe-users.txt
   del fitting_sessions maybe-fitting_sessions.txt
   del ai_generations maybe-ai_generations.txt
   ```

7. **Папки без пользователя.** Их файлы `deleteFiles` уже не удалит: это удалённые снова и
   созданные после копии. Имя папки, которое не uuid, печатается и не удаляется; при пустом
   `users-final.txt` (запрос не прошёл) не удаляется ничего:

   ```bash
   echo 'SELECT id FROM users;' | bash psql.sh | uuids > users-final.txt
   s3 s3 ls s3://<бакет приложения>/keep/users/ | awk '$1 == "PRE" { print $2 }' | sed 's,/$,,' > folders-all.txt
   uuids < folders-all.txt > folders.txt
   grep -vxFf folders.txt folders-all.txt | tr -c '[:print:]\n' '?'
   comm -23 folders.txt users-final.txt > orphans.txt
   wc -l < orphans.txt
   [ -s users-final.txt ] && while read -r id; do s3 s3 rm --recursive --only-show-errors "s3://<бакет приложения>/keep/users/$id/"; done < orphans.txt
   ```

8. **Запуск** того, что работало, и проверка: готовность api видна только изнутри контейнера, как в
   деплое, и приходит не сразу (до минуты):

   ```bash
   ssh -n ai-fitting "docker start $(paste -sd' ' running.txt)"
   ssh -n ai-fitting '. /opt/ai-fitting/.deploy-state && for i in $(seq 1 30); do docker exec "ai-fitting-$COLOR-api-1" node -e "fetch(\"http://127.0.0.1:3000/health/ready\").then((r) => process.exit(r.ok ? 0 : 1), () => process.exit(1))" && exit 0; sleep 2; done; exit 1' && echo "api готов"
   curl -fsS --retry 10 --retry-all-errors --retry-delay 2 https://lamoda-ai-fitting.ru/api/health/live && echo
   ```

   Только если напечаталось «api готов» — замок снять и деплои включить (иначе смотреть
   `docker logs` api, «На сервере»):

   ```bash
   ssh -n ai-fitting 'rmdir /opt/ai-fitting/.deploy-lock'
   gh workflow enable ci.yml -R EvaFridman/lamoda-ai-fitting
   gh workflow enable cd.yml -R EvaFridman/lamoda-ai-fitting
   ```

### Смена ключа age

Когда закрытый ключ мог утечь или запись в менеджере паролей под угрозой. Шаг 4 настройки целиком:
новая пара, новая запись в менеджере (старую не трогать), новый открытый ключ в
`BACKUP_AGE_RECIPIENT`. Он действует со следующего деплоя (слияния в `main`): `.env` сервера
переписывается, задача заменяется; до того копии шифруются старым ключом. Старый закрытый ключ
хранится ещё 14 дней после этого деплоя — копия живёт 7 дней, а версия, оставшаяся после её
перезаписи, ещё 7 (спека 0012 P29), — затем его запись удаляется. Копии, зашифрованные утёкшим ключом, читает и тот, у кого он есть, если получит доступ
к бакету бэкапов (список и чтение — только у главного ключа): поэтому менять сразу.

## Настройки GitHub и Sentry

Значения секретов не проходят ни через чат, ни через терминал на экране: команды ниже читают их из
файлов или генерируют на лету и сразу передают в GitHub (`gh secret set`). Проверка — только по
именам: `gh secret list`, `gh variable list`.

### Sentry (веб-интерфейс)

1. **Проекты:** Projects → Create Project → платформа **Next.js**, имя `lamoda-ai-fitting` (web);
   второй — платформа **Nest.js**, имя `lamoda-ai-fitting-api` (api и Temporal worker). Из
   настроек каждого проекта (Client Keys) понадобится его **DSN**.
2. **Токен для загрузки source maps:** Settings → Developer Settings → **Organization Tokens** →
   Create New Token (`lamoda-ai-fitting CI`). Отдельный токен для этого репозитория, чтобы его можно
   было отозвать, не задевая другие проекты. Показывается один раз — сразу в GitHub (шаг ниже).
3. **Slug организации** — в адресе `https://<slug>.sentry.io` или в Settings → General.

### Вход через Google (Google Cloud Console)

Вход на сайт — только через Google (спека 0013). Без клиента Google api в production не стартует,
а CD останавливается до сервера.

1. **Проект:** console.cloud.google.com → новый проект `lamoda-ai-fitting`.
2. **Экран согласия:** APIs & Services → OAuth consent screen (Google Auth Platform → Branding,
   Audience) → тип **External**, название сайта и почта поддержки; доступы только `openid`,
   `email`, `profile` (проверка Google для них не нужна). Пока приложение в статусе Testing,
   войти могут только добавленные тестовые пользователи; для всех — **Publish app**.
3. **Клиент:** Credentials (Clients) → Create OAuth client ID → тип **Web application**, имя
   `lamoda-ai-fitting`, Authorized redirect URIs: только
   `https://lamoda-ai-fitting.ru/api/auth/callback/google`. Адресов localhost у этого клиента нет
   (спека 0013 N49): локально входят через поддельный Google, сервис `oidc`. Чтобы проверить
   настоящий Google локально, в том же проекте заводят отдельный клиент `lamoda-ai-fitting-dev`
   с одним redirect `http://localhost:3001/api/auth/callback/google`; его значения — только в
   локальном `.env`, production-значения на машину разработки не попадают.

   Client ID — переменная `GOOGLE_CLIENT_ID`, Client secret — секрет `GOOGLE_CLIENT_SECRET`
   (ниже). Секрет показывается при создании; новый выпускается там же, а старый удаляется
   после деплоя с новым.

Client secret клиента Google («Вход через Google»; gh спросит значение, ввод не отображается). Без

Общий секрет nginx, web и api (заголовок `X-Proxy-Secret`): только с ним api верит адресу клиента и

#### Смена `PROXY_SECRET`

В два деплоя (спека 0006 F21). api верит и второму секрету, `PROXY_SECRET_NEXT` (тот же формат, не
равен `BETTER_AUTH_SECRET`; nginx и web его не отправляют, CD передаёт его только api). Когда nginx
пересоздаётся с новым секретом, работающая копия уже его принимает, даже если дальше деплой упадёт.

GitHub не показывает значение секрета, поэтому новое значение генерируется один раз в переменную
shell и оба шага делаются в одном терминале; значение не печатается.

Шаг 1: новое значение становится вторым секретом, затем деплой (CD вручную с хешем текущей версии,
как в разделе «Откат», или следующий мерж в `main`). nginx не пересоздаётся, новая копия api принимает
оба секрета.

```bash
secret="$(openssl rand -hex 32)"
printf '%s' "$secret" | gh secret set PROXY_SECRET_NEXT --env production
```

Шаг 2, после успешного деплоя шага 1: то же значение становится основным, второй секрет удаляется,
и снова деплой. nginx пересоздаётся (несколько секунд сайт не отвечает). Если этот деплой упадёт,
работающая копия принимает новый секрет nginx как второй; исправить причину и задеплоить снова.

```bash
printf '%s' "$secret" | gh secret set PROXY_SECRET --env production
gh secret delete PROXY_SECRET_NEXT --env production
unset secret
```

В `PROXY_SECRET` ставится только значение, которое уже прошло успешный деплой как
`PROXY_SECRET_NEXT`: иначе деплой остановится до пересоздания nginx («does not accept the new
PROXY_SECRET»), ничего не меняя. Пока сайт на версии старше 0006, такая копия не верит никакому
секрету, и смена ждёт возврата на 0006. Если значение потеряно (терминал закрыт), шаг 1 повторяется с новым
(`gh secret set` перезапишет старое) и снова ждёт успешного деплоя. Если секрет меняют из-за утечки,
шаг 2 делается сразу после шага 1, а упавший шаг 2 доводится до успешного деплоя без задержки: до
этого работающая копия верит и старому секрету.

## Сертификат HTTPS

До первого выпуска nginx работает на временном самоподписанном сертификате (`nginx/cert-init.sh`),
браузеры показывают предупреждение. Настоящий сертификат Let's Encrypt выпускается **один раз**, на
сервере, после первого деплоя (nginx должен отвечать на проверку домена). `init-cert.sh --staging`
обращается к тестовому серверу Let's Encrypt (лимиты мягкие), `init-cert.sh` без флага — к
настоящему (на email придут предупреждения):

```bash
ssh ai-fitting
cd /opt/ai-fitting
deploy/scripts/init-cert.sh --staging <email>
deploy/scripts/init-cert.sh <email>
```

Сначала всегда `--staging`: у настоящего сервера жёсткий лимит (5 одинаковых сертификатов в неделю).
Скрипт сам убирает временный или тестовый сертификат, при ошибке возвращает временный.

Дальше всё автоматически: контейнер `certbot` дважды в сутки продлевает сертификат, nginx раз в
6 часов перезагружается и подхватывает продлённый. Проверка:

```bash
ssh ai-fitting 'cd /opt/ai-fitting && docker compose -f deploy/compose/infra.yml --env-file .env \
  --profile server exec -T certbot certbot renew --dry-run --webroot -w /var/www/certbot'
```

Выпущен 2026-10-06 на `lamoda-ai-fitting.ru` и `www.lamoda-ai-fitting.ru`.

**HSTS** (`Strict-Transport-Security: max-age=31536000`): браузер, раз открывший сайт, год ходит на
него только по HTTPS и **не даёт пройти мимо ошибки сертификата**. Поэтому истёкший или сломанный
сертификат — это недоступный сайт для всех прежних посетителей, пока его не починят: следите за
письмами Let's Encrypt. `includeSubDomains` и `preload` не включены сознательно — их последствия
трудно отменить.

**Заголовки безопасности** (спека 0006 F9, F38): основной сервер nginx отдаёт на каждый ответ api,
web и свой собственный (413, 429, 503) `X-Content-Type-Options: nosniff`,
`Content-Security-Policy: frame-ancestors 'none'` и `Referrer-Policy: strict-origin-when-cross-origin`.
Редиректы (порт 80, `www`) их не отдают. Исключение — CSP страниц web (спека 0014 plan §5, O112):
`web/proxy.ts` ставит на каждую страницу полную политику с nonce на запрос, и nginx своей не
добавляет (`map` `$edge_csp`: если в CSP ответа уже есть `frame-ancestors 'none'`; любой другой
политике апстрима nginx добавляет свою). Две политики браузер
применяет обе, так что вторая ничего бы не дала. Скрипты страниц разрешены со своего домена, по
nonce и по хешам инлайн-скриптов статической оболочки (`web/src/shared/csp/shell-script-hashes.json`,
сверяет `scripts/check-web-shells.mjs` в `verify`); соединения — свой домен, Mixpanel
(`api-eu.mixpanel.com`) и Sentry (адрес из `NEXT_PUBLIC_SENTRY_DSN`). Нарушения видны только в
консоли браузера: отчётов о них сайт не собирает. Откат политики — revert `web/proxy.ts`.
У `/_next/image` (Next) и статики Swagger (Express) есть своя CSP без `frame-ancestors`, к ней nginx
добавляет свою. Браузер применяет обе политики, поэтому `proxy_hide_header Content-Security-Policy`
не ставят: он убрал бы песочницу Next для картинок. Ни одна `location` не задаёт свой `add_header`:
он отменил бы все заголовки уровня server, включая HSTS. Локально nginx нет, поэтому из этих
заголовков там есть только CSP страниц (с `'unsafe-eval'` в `next dev`).
