# 0002 Database schema: clarifications

Status: in progress (2026-10-07).

Decisions made by the owner. Each line is final unless the owner changes it here. The source design is
the owner's drawsql diagram (12 tables); the decisions below amend it.

## Scope

- C1. This spec: schema, migration and seed. No endpoints, no UI; the catalog API is a later spec.
- C2. This spec takes number `0002`; auth becomes `0003-auth`, because auth builds on the `users`
  table. The `0002-auth` reservation in spec 0001 is history and is not edited.

## Model

- C3. Primary keys are UUID v7, generated by the database (`uuidv7()`, PostgreSQL 18), not bigint:
  ids cannot be enumerated in URLs, and JSON needs no BigInt conversion.
- C4. Relations are one-to-many: brand → products, category → products, product → images,
  product → sizes, attribute → values, user → fitting sessions, session → generations.
  `product_attribute_values` (product ↔ attribute value) and `generation_products` (generation ↔
  product) are many-to-many junctions. A product has one category; categories are a flat list.
  A fitting session is not a chat, but holds several generations.
- C6. `users.gender` is an enum with the codes `male`, `female`; the Russian labels belong to the UI.
- C7. `users.phone` and `users.email` are both required and unique, as in the design.
- C9. Images are stored as object keys (`products/<id>/1.webp`), not full URLs. Renamed columns:
  `product_images.url` → `image_key`, `users.fitting_profile_image_url` → `fitting_profile_image_key`,
  `ai_generations.user_image_url` → `user_image_key`, `ai_generations.result_image_url` →
  `result_image_key`. The full URL is a base address from the environment (`MEDIA_BASE_URL`) plus the
  key; it lands with the first API that returns images. Until file storage exists, seed placeholder
  images live in `web/public/media/` and the site serves them under `/media/`.
- C9a. Serving placeholders from Next's static files was chosen over an nginx folder, a `media.`
  subdomain, object storage now, the api serving files, or no files yet: it needs no new
  infrastructure, and keys make the choice reversible (only `MEDIA_BASE_URL` changes). Real storage
  is chosen with photo upload.
- C9b. Placeholder images show clothing (the product's kind of garment) and are WebP files only.
- C9c. Exception to "files are changed with Edit and Write": the placeholder `.webp` files are
  binary, so a Node script in the task's scratchpad writes them, with `sharp` installed there (not in
  the repository) after the owner confirms the install. The owner looks at the images before the
  commit.
- C10. Fixes to the design: `ai_generations.updared_at` → `updated_at`; all timestamps are
  `timestamptz`; `created_at` and `updated_at` are filled automatically; `generation_products` gets
  no timestamps (a link is created with its generation). Prisma models are PascalCase and fields
  camelCase, mapped to the design's snake_case table and column names.
- C13. `products.rating` is nullable: NULL means no ratings yet (0 would read as a bad product).
  Ratings are set by the seed (later by import or admin); reviews are a later spec.
- C14. `ai_generations.user_image_key` is a snapshot of the photo the generation used (the profile
  photo or a one-off upload). Changing the profile photo does not change past generations.
- C15. A user has at most one active fitting session (`is_active = true`); the others are history.
- C17. `categories.description` is nullable. `ai_provider` and `ai_model` are free strings, not
  enums: a new model needs no migration. Products store `price` (rubles) and `discount` (percent);
  the price after the discount is computed by the catalog API, not stored.

## Data rules

- C8. On delete: the parts of a row go with it (cascade): a product's images, sizes and attribute
  links; a user's fitting sessions, their generations and the generations' product links. Reference
  data is protected (restrict): a brand or category with products, an attribute or attribute value
  in use, a product used in a generation cannot be deleted.
- C11. Unique: `(product_id, size)` in sizes, `(attribute_id, value)` in attribute values. Every
  foreign key has an index.
- C12. The database checks:
  - phone: `+79` and 9 digits (mobile numbers only, for SMS login). Input such as `8 (999) …` is
    normalized by the api (spec 0003);
  - email: lower case, `something@domain.zone`, at most 254 characters;
  - first name, last name, patronymic: 2–50 characters; letters (Cyrillic or Latin), with a hyphen,
    space or apostrophe only between letters;
  - date of birth: from 1900-01-01 up to today. The minimum age of 14 is checked by the api at
    sign-up (spec 0003);
  - category slug: lower-case Latin letters and digits in groups joined by single hyphens;
  - names (category, brand, product, attribute), article, size and attribute value: not empty, no
    leading or trailing spaces;
  - price greater than 0; discount 0–100; rating 0–5 or empty; stock and sort order 0 or more;
  - image keys: an allowlist (C22);
  - generation status: `completed` has a result image and no error; `failed` has an error message;
    `pending` and `processing` have neither;
  - error message: not empty, at most 1000 characters (C23).
- C21. The partial unique key of C15 looks like a full unique key to the generated client: a query
  by `{ userId }` alone (`findUnique`, `update`, `delete`, `upsert`, `connect`) may hit an archived
  session. Code always adds `isActive: true`; a comment in `schema.prisma` says so, and the tests of
  T3 cover a user with archived sessions and an active one. No lint rule.
- C22. Image keys (the four columns of C9) are relative object keys built from ASCII letters,
  digits, `.`, `_` and `-`, in segments joined by `/`; each segment starts with a letter or digit,
  and `..` is not allowed anywhere. A deny list (no leading `/`, no `..`, no `://`) was rejected:
  browsers and `new URL()` turn `\\host/x`, ` //host/x`, `javascript:…` or `%2e%2e/` into another
  host or path. The URL built from a key is checked by the first API that returns images (backlog).
- C23. `ai_generations.error_message` is `varchar(1000)` and not empty: it holds a short message or
  code, not a provider's raw response or a stack trace.

## Seed and deploys

- C5. The seed is a small invented catalog: about 5 categories, 5 brands and 30 products with sizes,
  attributes and placeholder images. No users. It is loaded locally and in production.
- C16. Every deploy runs the seed after `prisma migrate deploy`. The seed only creates rows that are
  missing, found by their natural keys (slug, article, name, product and size, …); it never updates
  or deletes existing rows, so edits made in the database survive (narrowed by C16b).
- C16b. (T4 review) Catalog reference rows (categories, brands, attributes, attribute values) are
  created only together with a new product that needs them, so a reference row renamed by hand
  stays renamed while its products exist. A product deleted by hand brings back, with it, the
  reference rows it needs under their seed names; a category whose slug alone was renamed (its name
  still taken) fails the seed with the product's article. Rows under an existing product (images,
  sizes, attribute links) are never re-added: deleting one is an edit too.
- C16a. Exception: a deploy of an image that has no seed (a rollback to a version from before this
  spec's seed) skips the step and logs "seed skipped", so such a rollback still works.

## Workflow

- C18. The drawsql diagram is updated by a patch the owner applies; the schema in code is the source
  of truth from then on.

- C19. The constraint tests get their database from Testcontainers: each test run starts a throwaway
  `postgres` container of the same image as compose, applies the migrations, and removes it. Same
  setup locally and in CI; the development database is never touched; Docker must be running for
  `verify`. Chosen over a CI service plus the compose database (two setups, `verify` depends on the
  running stack) and a separate command outside `verify` (against AC7).
- C20. The `test-writer` agent's rules change in T3: specs under `api/test/database/` (and only
  there) may use the throwaway database of C19; every other test still stubs Prisma and reaches no
  real service. The hook that limits its writes to spec files stays as it is; the test support files
  are written by the main session.
- C24. Found in the security review of T3: Testcontainers publishes its ports (the test database and
  Ryuk, its cleanup container, which holds the Docker socket and removes containers and volumes by
  label on request) on every interface while the tests run. Ryuk is disabled; the test database
  gets a random password per run and is removed by the tests' teardown. A killed run leaves its
  container behind (label `org.testcontainers=true`), removed by hand. Binding published ports to
  `127.0.0.1` with the Docker Engine setting `"ip"` was chosen first and dropped: Docker Desktop 29
  ignores it (checked: a port without an address still listens on every interface of the Mac), and
  Testcontainers 12.2 cannot set the address. A macOS firewall rule and accepting the exposure were
  the other options. A lint rule that keeps database specs on `createTestDatabase()` goes to the
  backlog.
